# Go Micro 프레임워크 평가 및 AI 에이전트 개발 분석 보고서

이 문서는 `njro` 프로젝트 관점에서 **Go Micro의 최근 방향성(AI Agent 전환)에 따른 프로젝트 적합성 평가**와 **Go Micro 기반 AI 에이전트 개발 가능성 및 아키텍처**를 정리한 분석 문서입니다.

---

## 1. Go Micro 프레임워크 현황 및 프로젝트(`njro`) 적합성 평가

### 1.1 Go Micro의 최근 변화
* **정체성 전환**: Go Micro(`micro/go-micro`, `go-micro.dev`)는 최근 마이크로서비스 툴킷을 넘어 **"Agent Harness & Service Framework"**로 정체성을 재정의했습니다.
* **주요 초점**: Model Context Protocol(MCP) 게이트웨이 내장, Agent-to-Agent(A2A) 통신, 에이전트 내구성 워크플로우(Durable Flows), 자연어 기반 CLI(`micro chat`) 등 AI 에이전트 지원 기능에 집중하고 있습니다.
* **기존 마이크로서비스 기능**: 여전히 유지되고 있으나, 순수 범용 웹/엔터프라이즈 백엔드 관점의 기능 개선이나 커뮤니티 지원은 축소되었습니다.

### 1.2 `njro` 프로젝트와의 괴리
* **현재 프로젝트 성격**: 게시판(`service/board`), 게시글(`service/post`), 댓글(`service/comment`), 계정(`service/account`), 검색(`service/search`), 이메일(`service/emailer`) 등으로 구성된 **전형적인 RDBMS(GORM) 기반 커뮤니티/비즈니스 백엔드 MSA**입니다.
* **핵심 요구사항**: 안정적인 gRPC/HTTP 통신, DB 트랜잭션, 커넥션 풀링, 인증/인가, 로깅/메트릭 등 견고한 서버 인프라가 필수적입니다.
* **결론**: AI 에이전트 오케스트레이션이 필요하지 않은 순수 비즈니스 백엔드에서, 에이전트용 런타임으로 변모한 Go Micro를 계속 유지하는 것은 불필요한 복잡성과 유지보수 부담을 가중시킵니다.

### 1.3 히스토리 관점에서의 기술 부채 리스크
1. **잦은 방향 전환**:
   * v1/v2 시절: Go 대표 MSA 라이브러리
   * v3 시절: M3O 클라우드 플랫폼 종속 구조로 전환하며 레포 분열(`micro/micro` vs `asim/go-micro`)
   * 최신: AI Agent 프레임워크로 급선회
2. **의존성 충돌(Dependency Hell)**:
   * 프로젝트의 `go.mod`에 `asim/go-micro/v3`, `micro/go-micro/v2`, `micro/micro/v3`가 혼재
   * `README.md`에 명시된 `grpc@v1.30.0` 다운그레이드 이슈처럼 Protobuf/gRPC 버전 충돌 문제 잔존

### 1.4 권장 마이그레이션 대안
| 대안 | 장점 | 적용 권장 상황 |
| :--- | :--- | :--- |
| **표준 gRPC-Go + Buf** | 프레임워크 종속 없는 업계 표준, 완벽한 호환성 및 장기 안정성 | 특정 프레임워크 락인을 피하고 순수 표준으로 구축할 때 (가장 권장) |
| **Go-Kratos** | Clean Architecture / DDD 기본 지원, gRPC/HTTP 듀얼 서빙, 안정적인 엔터프라이즈 지원 | 기존 MSA 구조를 유지하며 성숙한 마이크로서비스 프레임워크를 원할 때 |
| **Go-Zero** | 강력한 코드 제너레이션, 캐시/동시성/레이트리밋 등 내장 기능 풍부 | 빠른 API 개발 및 성능 최적화가 필요할 때 |
| **모듈러 모놀리스 (Modular Monolith)** | 네트워크/배포 복잡도 제거, 단순한 로컬 트랜잭션 | 서비스 간 트래픽이나 팀 규모 대비 MSA 오버헤드가 과도할 때 |

## 2. Go Micro 의존성을 활용한 AI 에이전트 개발 분석

만약 Go Micro를 활용하여 AI 에이전트를 개발한다면, **"기존 마이크로서비스들을 LLM의 도구(Tool)로 부리는 고성능 분산 에이전트"** 형태로 구축할 수 있습니다.

### 2.1 아키텍처 개요
Go Micro의 에이전트는 독립된 서비스 노드로 동작하며, 서비스 디스커버리를 통해 기존 마이크로서비스의 RPC 엔드포인트를 MCP/JSON Schema 도구로 자동 인식합니다.

```
                      ┌────────────────────────────────────────┐
                      │          Go Micro Agent Node           │
                      │  ┌────────────┐   ┌─────────────────┐  │
                      │  │ LLM Engine │   │ Agent Memory    │  │
                      │  │ (Claude /  │   │ (Redis/Postgres)│  │
                      │  │  OpenAI)   │   └─────────────────┘  │
                      │  └──────┬─────┘                        │
                      └─────────┼──────────────────────────────┘
                                │ Service Discovery (Registry)
                ┌───────────────┼───────────────┬──────────────┐
                ▼               ▼               ▼              ▼
         [service/post]  [service/board] [service/search] [service/emailer]
          (MCP / RPC)     (MCP / RPC)     (MCP / RPC)    (MCP / RPC)
```

### 2.2 `njro` 서비스와 연계한 에이전트 유스케이스

#### ① 커뮤니티 모니터링 & 운영 에이전트 (Moderator Agent)
* **목적**: 유해 게시글 탐지, 스팸 차단, 사용자 제재 자동화.
* **시나리오**:
  1. `service/post`, `service/comment`의 새 글/댓글 이벤트(Pub/Sub) 구독.
  2. 에이전트(LLM)가 맥락을 분석하여 광고/스팸/악성 게시글 여부 판별.
  3. 위반 확인 시 `post.UpdateStatus()` 호출로 블라인드 처리.
  4. `service/emailer`를 호출해 작성자에게 제재 안내 메일 자동 발송.

#### ② 자연어 기반 통합 관리 비서 (Operations Assistant Agent)
* **목적**: 관리자가 챗봇/자연어로 백오피스 작업을 실행.
* **시나리오**:
  * 관리자 요청: *"최근 3일간 가입자 중 게시글을 1개도 작성하지 않은 사용자 목록을 추출해서 리인게이지먼트 메일 발송해줘."*
  * 에이전트 작업 분해 및 실행:
    1. `account.ListUsers()`로 가입자 필터링
    2. `post.CountByUser()`로 활동 내역 대조
    3. `emailer.SendEmail()`로 대상자에게 맞춤 메일 발송

#### ③ 지식 검색 및 큐레이션 에이전트 (Curator Agent)
* **목적**: 방대한 커뮤니티 게시글을 사용자 질의에 맞춰 탐색 및 요약 제공.
* **시나리오**:
  * 사용자 질의: *"MSA 환경에서 분산 트랜잭션 구현과 관련된 게시글 핵심 내용 정리해줘."*
  * 에이전트 동작: `service/search`로 관련 문서 검색 -> `service/post` 본문 수집 -> 핵심 정리 및 답변 반환.

#### ④ 분산 멀티 에이전트 협업 (Agent2Agent, A2A)
* 마이크로서비스처럼 각기 다른 역할의 에이전트들이 네트워크를 통해 협업:
  * **Draft Agent**: 외부 뉴스나 기술 문서를 수집하여 글 초안 작성
  * **Reviewer Agent**: 초안의 내용 검증 및 `service/tags`를 통한 자동 태깅
  * **Publisher Agent**: 최종 검토 완료 후 `service/board`에 게시 등록

## 3. 종합 평가 및 결론

1. **에이전트 개발 관점의 장점**:
   * Python 없이 **Go 언어의 고성능, 단일 바이너리, 낮은 메모리 사용량**을 살려 대규모 에이전트 운영 가능.
   * 기존 Go RPC 엔드포인트를 별도 래핑 없이 즉시 LLM Tool(MCP)로 연결 가능.

2. **일반 백엔드 프로젝트 관점의 결론**:
   * `njro` 프로젝트의 핵심 목적이 **안정적인 커뮤니티/게시판 비즈니스 백엔드**라면, 현재의 Go Micro는 **오버스펙이자 방향성이 어긋난 의존성**입니다.
   * 따라서 일반 백엔드 API 서비스는 **표준 gRPC-Go** 또는 **Go-Kratos/모듈러 모놀리스**로 전환하고, 향후 AI 에이전트가 필요해지는 시점에 별도의 전용 레이어로 도입을 검토하는 것이 바람직합니다.
